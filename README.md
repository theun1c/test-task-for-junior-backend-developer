# Task Service

Сервис для управления задачами с HTTP API на Go.

Текущая версия модуля поддерживает:

- обычные разовые задачи
- периодические задачи по календарным правилам
- выборку задач на конкретные дату и время
- завершение конкретного календарного вхождения
- защиту от дублей завершённых вхождений

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздайте volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из директории `migrations/` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks?calendar_at=25.03.2026 10:10`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`
- `POST /api/v1/tasks/{id}/occurrences/complete`

## Что считается готовым в модуле

Сейчас модуль умеет:

- сохранять `periodicity_settings` в задаче
- хранить календарный интервал задачи через `schedule_start_at` и `schedule_end_at`
- интерпретировать обычную задачу как разовое календарное событие по `schedule_start_at`
- интерпретировать периодическую задачу как одно календарное правило без дублирования строк в `tasks`
- возвращать задачи на выбранные дату и время через `GET /tasks?calendar_at=...`
- завершать конкретное календарное вхождение через `POST /tasks/{id}/occurrences/complete`
- возвращать `409 Conflict` при повторной попытке завершить то же самое вхождение

## Ключевая модель данных

### Таблица `tasks`

В `tasks` хранится одна запись задачи:

- базовые поля задачи
- `state`
- `schedule_start_at`
- `schedule_end_at`
- `periodicity_settings`

Поле состояния задачи называется `state` и поддерживает значения:

- `active`
- `paused`
- `archived`

В календарную выборку попадают только задачи со `state = active`.

### Таблица `task_completed_occurrences`

Отдельная техническая таблица хранит завершённые календарные вхождения:

- `task_id`
- `scheduled_for`
- `completed_at`

На уровне БД уникальность обеспечивается парой `(task_id, scheduled_for)`.

## Принятые решения

### 1. Одна задача, а не множество сгенерированных копий

Один из возможных вариантов реализации предполагал генерацию новых строк в `tasks` на каждую будущую дату. От этого подхода выполнен отказ.

Принятое решение:

- одна запись в `tasks` хранит календарное правило
- приложение само вычисляет, должна ли задача отображаться на выбранные дату и время
- завершённые даты хранятся отдельно

Почему так:

- таблица `tasks` не разрастается копиями
- нет лишнего дублирования данных
- проще управлять одной задачей как сущностью

### 2. `periodicity_settings` хранится в `JSONB`

Настройки периодичности хранятся в `tasks.periodicity_settings` типа `JSONB`.

Почему так:

- для проекта это минимальное решение
- не требуется отдельная таблица только под настройки
- структура настроек остаётся гибкой

При этом в Go используется typed-модель, а не `map[string]any`, чтобы не потерять типобезопасность и читаемость.

### 3. `status` заменён на `state`

Старое поле `status` было хорошо для простого CRUD, но стало плохо описывать календарную модель.

Почему заменили:

- `status` звучал как состояние конкретного выполнения
- фактически поле стало описывать состояние записи задачи целиком
- завершение конкретной даты хранится отдельно, значит у записи задачи и у календарного вхождения разные смыслы

Поэтому теперь:

- `state` описывает саму запись задачи
- завершение календарной даты хранится отдельно

### 4. Обычная задача тоже участвует в календаре

Если задача не имеет `periodicity_settings`, но имеет `schedule_start_at`, она считается разовым календарным событием.

Правило:

- задача попадает в `GET /tasks?calendar_at=...`, если `calendar_at == schedule_start_at` с точностью до минуты

### 5. Повторное завершение вхождения считается конфликтом

Раньше дубль завершения мог быть тихо проигнорирован.

Теперь:

- повторное завершение той же пары `task_id + scheduled_for` возвращает `409 Conflict`

Это лучше, потому что клиент явно понимает, что действие уже было выполнено раньше.

## Процесс разработки

Фича была реализована по шагам:

1. Анализ текущего CRUD-модуля задач и существующей схемы БД.
2. Добавление доменной модели периодичности.
3. Протягивание `periodicity_settings` через repository, usecase, transport и OpenAPI.
4. Фиксация правила, что задача не должна дублироваться по датам.
5. Добавление календарного интервала `schedule_start_at` / `schedule_end_at`.
6. Добавление технической таблицы завершённых календарных вхождений.
7. Реализация выборки задач по календарной дате и времени.
8. Расширение календарной выборки на обычные задачи.
9. Переименование `status` в `state`.
10. Добавление явного `409 Conflict` на повторное завершение одного и того же вхождения.

## Основные сложности

### Семантика задачи и семантика календарного вхождения

Главная сложность заключалась в следующем:

- задача как запись живёт долго
- календарное вхождение относится к конкретной дате и времени

Если смешать эти два смысла в одном поле, модель быстро становится нелогичной.

В результате зафиксировано следующее:

- `state` относится к записи задачи
- завершение даты относится к отдельной технической таблице

### Как не раздувать таблицу `tasks`

Массовое создание копий задач под каждую дату ухудшает модель данных и усложняет сопровождение.

Выбранный подход:

- хранить одну задачу
- вычислять календарное совпадение на уровне приложения
- отдельно хранить только завершённые вхождения

### Что делать с обычными задачами

Отдельно зафиксировано требование, что календарь должен видеть не только периодические задачи.

Поэтому:

- обычная задача без `periodicity_settings` участвует в календаре по `schedule_start_at`

## Допущения и ограничения

Сейчас в модуле действуют такие правила:

- формат календарных даты и времени в HTTP API: `dd.mm.yyyy hh:mm`
- сравнение дат в календаре выполняется с точностью до минуты
- парсинг и форматирование идут в локальной timezone процесса через `time.Local`
- `schedule_end_at` допустим только для периодической задачи
- если `periodicity_settings == nil`, задача считается обычной
- если у обычной задачи нет `schedule_start_at`, в календарную выборку она не попадёт
- `paused` и `archived` не попадают в календарную выборку
- `monthly_days` поддерживает только дни `1..30`
- завершённое вхождение больше не попадает в календарную выборку

## Поддерживаемые типы периодичности

- `daily`
- `monthly_days`
- `specific_datetimes`
- `month_day_parity`

### `daily`

Пример:

```json
{
  "type": "daily",
  "every_n_days": 2
}
```

### `monthly_days`

Пример:

```json
{
  "type": "monthly_days",
  "days_of_month": [1, 15, 30]
}
```

### `specific_datetimes`

Пример:

```json
{
  "type": "specific_datetimes",
  "specific_datetimes": ["25.03.2026 10:10", "27.03.2026 10:10"]
}
```

### `month_day_parity`

Пример:

```json
{
  "type": "month_day_parity",
  "day_parity": "even"
}
```

## Примеры запросов

### 1. Создать обычную разовую задачу

```bash
curl -X POST http://localhost:8080/api/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Пройти собеседование",
    "description": "Подготовить ответы и документы",
    "state": "active",
    "schedule_start_at": "25.03.2026 10:10"
  }'
```

Ожидаемое поведение:

- задача сохранится как обычная
- в календаре появится ровно на `25.03.2026 10:10`

### 2. Создать периодическую ежедневную задачу

```bash
curl -X POST http://localhost:8080/api/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Проверить отчёты",
    "description": "Ежедневная проверка",
    "state": "active",
    "schedule_start_at": "25.03.2026 09:00",
    "schedule_end_at": "31.03.2026 09:00",
    "periodicity_settings": {
      "type": "daily",
      "every_n_days": 1
    }
  }'
```

### 3. Получить задачи на конкретные дату и время

```bash
curl "http://localhost:8080/api/v1/tasks?calendar_at=25.03.2026%2010:10"
```

Ожидаемое поведение:

- вернутся активные задачи, которые совпадают с этой датой и временем
- вернутся и обычные задачи, если их `schedule_start_at` совпадает
- завершённые на этот момент задачи не вернутся

### 4. Завершить конкретное календарное вхождение

```bash
curl -X POST http://localhost:8080/api/v1/tasks/1/occurrences/complete \
  -H "Content-Type: application/json" \
  -d '{
    "scheduled_for": "25.03.2026 10:10"
  }'
```

Ожидаемое поведение:

- если задача действительно существует на эту дату и время, сервер вернёт `204 No Content`
- после этого это вхождение пропадёт из календарной выборки

### 5. Повторно завершить то же самое вхождение

```bash
curl -i -X POST http://localhost:8080/api/v1/tasks/1/occurrences/complete \
  -H "Content-Type: application/json" \
  -d '{
    "scheduled_for": "25.03.2026 10:10"
  }'
```

Ожидаемое поведение:

- сервер вернёт `409 Conflict`
- тело ответа будет содержать ошибку

Пример:

```json
{
  "error": "task occurrence already completed"
}
```

### 6. Приостановить задачу

```bash
curl -X PUT http://localhost:8080/api/v1/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Пройти собеседование",
    "description": "Подготовить ответы и документы",
    "state": "paused",
    "schedule_start_at": "25.03.2026 10:10"
  }'
```

Ожидаемое поведение:

- задача сохранится
- в обычном `GET /tasks` она будет видна
- в `GET /tasks?calendar_at=...` она больше не попадёт, пока не станет `active`

## Как протестировать модуль вручную

### Вариант 1. Через Swagger

1. Поднять сервис через `docker compose up --build`.
2. Открыть `http://localhost:8080/swagger/`.
3. Создать обычную задачу.
4. Создать периодическую задачу.
5. Проверить `GET /api/v1/tasks?calendar_at=...`.
6. Завершить вхождение через `POST /api/v1/tasks/{id}/occurrences/complete`.
7. Повторить тот же запрос и убедиться, что приходит `409 Conflict`.

### Вариант 2. Через `curl`

1. Создать разовую задачу.
2. Создать периодическую задачу.
3. Выполнить календарную выборку.
4. Завершить одно из вхождений.
5. Повторить календарную выборку.
6. Повторно завершить то же вхождение и проверить `409`.
