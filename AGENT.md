# AGENT.md

## Роль

Ты работаешь как агент-разработчик в существующем Go-проекте.

## Цель

Помогать в реализации фич и исправлений аккуратно, небольшими шагами и без лишних изменений.

## Основные правила

1. Перед началом работы изучай:
   - `docs/codex/project/CONTEXT.md`
   - файлы текущей фичи `docs/codex/feat/feat-NNNN/` (`SPEC.md`, `TASKS.md`), если они есть
2. Всегда сначала понимай существующую реализацию, потом предлагай изменения.
3. Следуй текущей архитектуре и стилю проекта.
4. Не делай лишних рефакторингов, если они не нужны для задачи.
5. Не меняй несвязанные части проекта.
6. Предпочитай простые и понятные решения.
7. Если есть несколько вариантов, выбирай самый минимальный рабочий.
8. Если в задаче есть неоднозначность, явно фиксируй принятое допущение в отдельный файл `docs/codex/DECISIONS.md`.

## Подход к работе

1. Изучи текущий код
2. Найди точку внесения изменений
3. Составь короткий план
4. Предоставь план реализации и примеры разработчику
5. После апрува реализуй решение небольшими шагами
6. Кратко опиши, что было сделано

## Требования к изменениям

- Изменения должны быть локальными
- Код должен быть читаемым
- Новая логика не должна ломать старую
- Публичное поведение API без необходимости не менять
- Не добавлять зависимости без явной причины

## Работа с кодом

- Используй существующие структуры, интерфейсы и паттерны проекта
- Если логика новая и изолируемая — выноси её в отдельный сервис/пакет
- Не дублируй код без необходимости
- Валидацию держи ближе к входу данных
- Бизнес-логику не размещай в handler'ах, если в проекте уже есть сервисный слой

## Работа с БД

- Изменения схемы должны быть минимальными
- Новые поля и таблицы добавляй только если они действительно нужны
- Всегда думай о совместимости с текущими данными
- Не усложняй схему заранее

## Формат ответов агента

Когда выполняешь задачу, отвечай кратко и по делу:

1. что изучено
2. какой план
3. что изменено
4. какие остались вопросы или риски
